# DXLib版の起動時間・スプラッシュ調査

調査日: 2026-09-21。製品コードの変更は行わず、Release版と `playtest/startup-20260921/` 以下の独立した検証用コピーで調査した。

## 結論

現在のSandboxは初回描画完了まで約0.96秒。そのうちDXLib初期化が約0.57秒、初期化後の準備・初回描画が約0.25秒を占める。単純な設定変更による大幅な短縮は確認できなかった。

黒画面対策にはスプラッシュを入れられる。推奨構成は、Windows側の軽いスプラッシュを先に表示し、DXLibの本体ウィンドウは非表示で初期化、最初のフレームを用意してから本体を表示する方式。初期化直後にDXLibだけでスプラッシュを描く簡易方式も可能だが、DXLib初期化中の待ち時間には届かない。

今回確認したのは、非表示でのDXLib初期化、簡易スプラッシュ描画、ScreenFlip成功、ウィンドウの表示切替、描画バッファのPNG確認まで。初期化前のWindowsスプラッシュは設計案であり、製品への組み込みや画面遷移全体の検証はまだ行っていない。

## 測定条件と結果

- Windows 11 / Intel Core Ultra 5 125H / Intel Arc Graphics、同梱DXLib 3.24f、.NET 10 Release。
- Sandboxの既定シーン1、1280×720、ウィンドウ表示、VSyncなし、FPS無制限、既定の更新スレッド設定。
- `--backend dxlib --boot-timing --quit-after-sec 0.25`。実行時の作業ディレクトリは `Release`。
- 比較する設定を交互に各6回起動し、各設定の最初の1回を除外した5回の中央値を採用。再起動直後のコールドスタートは評価していない。
- `BootTimer`の合計値はプロセス開始から最初の描画完了までの概算。ウィンドウが出る前も含むため、黒画面が実際に見えている時間とは異なる。ランタイムの欄も厳密なMain到達時刻ではなく、BootTimerを最初に参照した時点までを含む。
- シーンや素材が異なるゲーム、フルスクリーン、他PCの時間はこの結果から保証できない。

| 設定 | 初回描画までの中央値 | 範囲 | DxLib_Init中央値 | Init終了後の中央値 |
|---|---:|---:|---:|---:|
| 現状 | 955.6 ms | 943.6–1011.0 ms | 566.0 ms | 250.3 ms |
| `--no-log-overlay` | 965.8 ms | 931.7–980.5 ms | 570.8 ms | 237.8 ms |

列ごとに中央値を取っているので、各列はそのまま加算できない。ログ非表示は初期化後の時間を約12.5 ms減らしたが、起動全体ではばらつきに埋もれる。

元データ: `../playtest/startup-20260921/baseline.csv`、`normal-*.stdout.txt`、`no-log-*.stdout.txt`。

## ボトルネックの切り分け

### DXLib初期化

既に `DXLib/DxLibPlatform.cs` で `SetUseDirectInputFlag(0)` を設定済み。DirectInputを無効化する対策を追加しても変化はない。

製品と同じ初期化設定を持つSTA検証プログラムで、ネイティブログを有効にした診断実行では、次の区間が見られた。ログ有効時は計測負荷が増すため、上の本体ベンチマークと直接比較しない。

- CPU情報取得の区間: 約100 ms。
- WASAPI初期化: 約95 ms。
- Direct3Dデバイス、スワップチェーン、シェーダー等の準備: 約190 ms。
- この診断実行では初期化開始9 ms、ウィンドウ表示176 ms、初期化終了637 ms。黒いウィンドウが初期化の途中から表示される構造が分かる。

音声だけを無効にした独立プローブの比較:

| 検証用設定 | DxLib_Init中央値 |
|---|---:|
| 通常 | 588.6 ms |
| `SetNotSoundFlag(1)` | 483.0 ms |

約106 msの差がある。ただしこれは音声機能を止めた診断であり、一般のゲーム向け高速化としてそのまま採用できない。DXLib音声を一切使わないアプリに限り、明示的な無音起動設定として検討できる。音声の後付け初期化は今回未検証。

元データ: `../playtest/startup-20260921/native.csv`、`probe-*.stdout.txt`、`Log.txt`。最初のMTA試作ログではCOM初期化失敗が出たため、その試作値は採用せず、STAに修正したプローブで比較を実施した。

### フォントの作成時間と初回描画を混同しない

現行 `Core/Font.cs` は `CreateFont` の終了後にだけ `BootTimer.Mark` を置いている。従って「フォント生成 Yu Gothic 108 ms」と表示されても、その108 msは前のマーク以降のシーン描画などを含む。

独立コピーにコンストラクタ開始マークを加えた実行では、Yu Gothic UI 13pxは約2.9 ms、Yu Gothic 16pxは約3.5 msだった。一方で両者の作成の間に約93.6 msがあり、これはフォント生成ではなくシーンの初回描画などの区間である。DXLibのフォントハンドル作成を、Raylibの日本語アトラス生成と同じコスト構造と考えるべきではない。

DXLibは使用する文字の初回描画時に文字画像を取得しキャッシュする。この仕組みは[DXLib管理人の説明](https://dxlib.xsrv.jp/cgi/patiobbs/patio.cgi?mode=view&no=4239)でも確認できる。ただし今回の約94 ms全体を文字描画だけに帰属させることもできない。

通常文字の8×8アンチエイリアスを4×4にした検証用コピーも比較した。縁取り専用ハンドルの設定は変更していない。

| 検証用コピー | 初回描画までの中央値 | Init終了後の中央値 |
|---|---:|---:|
| 8×8 | 982.9 ms | 264.1 ms |
| 4×4 | 950.0 ms | 257.8 ms |

初期化後の差は約6.3 msで、範囲も大きく重なる。全体の約33 ms差にはDXLib初期化やランタイム開始のばらつきが含まれ、文字品質変更の効果とは断定できない。起動対策として品質を下げる根拠は弱いので採用しない。画質の比較検証も未実施。

元データ: `../playtest/startup-20260921/aa.csv`、`aa8-*.stdout.txt`、`aa4-*.stdout.txt`。検証コピーのみ環境変数 `ASTRUM_PROBE_AA4=1` で4×4に切り替わる。

## スプラッシュの選択肢

| 方法 | 表示できる時点 | 効果と制約 |
|---|---|---|
| 本体を非表示で初期化し、初回描画後に表示 | ゲーム画面が完成した時点 | 黒い本体ウィンドウを避けられるが、その間の起動反応がない |
| DXLib初期化直後に簡易スプラッシュを描画 | DxLib_Initの後 | 今回の約250 msの準備・初回描画区間を覆える。初期化中は表示できない |
| Windows側の別スプラッシュを先に表示 | DXLib初期化の前 | 初期化待ちも覆える。ウィンドウ管理と失敗・終了時の後始末が必要 |

非表示での初期化は、`DxLib_Init` 前に `SetWindowVisibleFlag(FALSE)`、描画後に `SetWindowVisibleFlag(TRUE)` を呼ぶ方法が[DXLib公式掲示板で案内されている](https://dxlib.xsrv.jp/cgi/patiobbs/patio.cgi?mode=view&no=5260)。同梱DLLのプローブでも、Init後の `IsWindowVisible=False`、描画・表示切替後の `True`、ScreenFlip成功を確認した。

DXLib初期化直後の簡易スプラッシュは、新しいフォントや画像をロードせず、背景・線・既存フォントだけで描画した。通常表示で描画とScreenFlipが中央値10.4 ms、非表示からの表示切替を含めて中央値14.0 ms。PNG保存を行った実行は別で、これらの中央値に含めない。

![描画バッファで確認した簡易スプラッシュ](../playtest/startup-20260921/splash-probe.png)

この画像は機能検証用であり最終デザインではない。連続したデスクトップ録画は行っていないため、DWM表示まで含めた黒フレームの完全排除や画面遷移の滑らかさは未検証。

Windows側のスプラッシュは、Win32/GDIの小さなウィンドウに埋め込み画像やタイトルを描けばDXLibに依存しない。初期表示時の描画は[MicrosoftのShowWindow / UpdateWindowの説明](https://learn.microsoft.com/en-us/windows/win32/winmsg/using-windows)に沿って行える。実装案は次のとおり。

1. `GameApp.Run` の引数検証・設定反映後、`CreatePlatform` の前に表示する。ヘルプ表示や不正引数の終了では表示しない。
2. スプラッシュ専用UIスレッドでメッセージを処理し、DXLib初期化中も再描画に応答する。DXLibの初期化・描画は従来のメインスレッドに残す。
3. 本体を非表示で初期化し、初回ScreenFlipが成功してから本体を表示、スプラッシュを閉じる。固定の最低表示時間は設けない。
4. 初期化失敗、描画失敗、起動中の終了でもスプラッシュを必ず閉じる。本体のエラー表示まで非表示のままにしない。
5. 表示する文字は「起動中」等にし、実測根拠のない進捗率は出さない。完了段階の表示は可能。
6. DPI・複数モニター・フォーカス・フルスクリーン・起動中終了を実機で確認する。

## 実装する場合の優先順位

1. 起動時の見え方を改善するなら、Windowsスプラッシュと本体の遅延表示を先に実装する。ゲーム側の設定で有効化できる形が適する。
2. 実処理時間の短縮は、計測を開始・終了の対に直し、初回描画区間のJIT、文字初回描画、画像生成を個別に測る。初期化前スプラッシュ、DXLib初期化終了、初回ゲーム画面の3時刻を別々に記録する。
3. ReadyToRun発行と素材の事前生成・段階読み込みを候補にする。ReadyToRunは今回再測定していないため、本資料では改善値を提示しない。
4. ログを消す、文字品質を下げる、音声を全体で無効化する変更は、今回の通常起動対策には採用しない。

ReleaseのSandbox、STAプローブ、比較用DXLibコピーはいずれもビルド成功（警告0・エラー0）。元の作業ツリーには既存変更があり、調査中にも他作業による変更を確認したため、製品ソースの修正・巻き戻しは行っていない。測定値は今回実行したバイナリに対する結果で、今後再ビルドした最新版にそのまま適用しない。
